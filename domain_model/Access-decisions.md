# Решения: ролевая модель и сервис аутентификации

Ответы на вопросы из `Access-questions.md`, номера те же. Бэк-сервис — основной бэкенд платформы (gefest). После обсуждения решения переносятся в `Access.md`, затем в `Main.md`. Таблицы по этим решениям — `Access-schema.md`.

## Сервис аутентификации

### 1. Граница сервиса
В сервисе аутентификации — номер человека (`Person`), `AuthIdentity`, сессии; в бэк-сервисе — профиль человека (решение 34), `Membership`, `Audience`, `AudienceMembership` (решение 24), `AccessGrant`, `Invitation`, `AccessRequest`. Правило: «как ты входишь» — сервис аутентификации; «кто ты на платформе» и «что тебе можно в мемориале» — бэк-сервис. Сервис аутентификации выдаёт и проверяет токены, а бэк-сервис проверяет права человека в мемориале. `ApiToken` убран — решение 12а.

### 2. Что в токене
В токене только «кто это» — человек и канал (решение 32); областей доступа нет (решение 9); роли и аудитории бэк-сервис проверяет по БД на каждом запросе, иначе отзыв доступа не сработает сразу. Так устроены системы с правами на объекты (GitHub, Google Drive, Notion); роли в токене — подход корпоративного входа с немногими общими ролями.

### 3. Возврат на мемориал
Возвращаем только на хосты из `TenantHost`; одноразовый код живёт около минуты и годится одному хосту; `state` + PKCE. Как работают код и PKCE — `vk-login-pkce.md`.

### 4. Сессии
Сессия живёт час без активности: каждый запрос продлевает её, после часа простоя нужен вход заново. «Выйти» — выход из всех мемориалов: сервис аутентификации закрывает свою сессию и все сессии мемориалов, выданные от неё.

### 5. Второй способ входа
Если этот Telegram уже привязан к другому человеку — запрещаем: «Этот способ входа уже используется другой учётной записью». Слияние учёток — потом. Тогда же — сверка учёток по номеру телефона из VK и Telegram: только подсказка «у вас уже есть учётная запись, вход через VK», без автоматической привязки (номера переходят к другим людям); хранится не номер, а HMAC от него.

### 6. Потеря доступа
Как владелец восстанавливает вход, если потерял VK, — отложено, подумаем потом.

### 7. Согласие на обработку данных
Храним ли, когда человек дал согласие и на какую версию политики, и что делать с его записями при удалении аккаунта, — отложено, сделаем потом. Предложение: история согласий отдельными записями в сервисе аутентификации; при удалении аккаунта человек выбирает — удалить его записи или оставить без имени; владелец не может удалить аккаунт, пока не передаст роль владельца другому (решение 13). Какие согласия и к какому сроку — решение 48.

## Боты и их токены

Чат с платформой — только наши боты в Telegram и VK; позже, возможно, другие мессенджеры. WhatsApp не делаем: платный, сложно платить из России, под угрозой блокировки в России. Человек пишет боту в чате, бот добавляет посты в мемориал. Claude, ChatGPT и другие внешние приложения к платформе не подключаются.

Приложение бота — отдельный сервис: приём сообщений + языковая модель + список действий (инструментов) модели. Каждое действие бот выполняет запросами к обычному API бэк-сервиса, как фронт. Модель может сделать только то, что есть в этом списке: модели нужны крупные действия вместо мелких запросов API, опасных действий в списке просто нет. Отдельно от бэк-сервиса — чтобы нагрузка от ботов не задевала сайт.

MCP-сервера нет: он нужен, чтобы к платформе подключались чужие агенты, а их не будет. Если понадобятся — список действий бота можно будет выделить в MCP-сервер.

### 8. Как бот получает токен
- Бот узнаёт человека по id отправителя сообщения (`AuthIdentity`) и получает токен у сервиса аутентификации внутри системы — без ключей, без OAuth и без экрана подтверждения. Проверить при реализации: id отправителя в боте совпадает с id из входа на сайт. Решить потом: что делает бот, если человек ещё не входил на сайт.
- Защита в три слоя: модель может вызвать только действия из списка бота (опасных нет, удаление — с подтверждением в чате); бэк-сервис сам отклоняет запрещённые боту действия (решение 37); бэк-сервис проверяет права человека.
- Новый мессенджер — новый адаптер приёма и отправки сообщений в приложении бота и, если нужно, новый вид `AuthIdentity.provider`; список действий и права не меняются.
- Языковая модель у ботов — российского поставщика по API, своей модели пока нет (решение 48). Claude и ChatGPT по API из России недоступны.
- Ключи из настроек для своих скриптов — потом, если понадобятся.

### 9. Что может бот
Областей доступа у токена нет: они нужны, когда человек сам выбирает, что разрешить чужой программе, а у нашего бота набор действий всегда один. Что может бот, задаёт список его действий: читать то, что видит человек; создавать посты и контент там, куда человеку можно добавлять, менять и удалять созданное ботом; загружать файлы; скачивать оригиналы, если это право есть у человека; создать мемориал — человек становится владельцем. Никогда: открывать контент другим, менять аудитории, участников, права и настройки, трогать не своё.

Действие бота выполняется, только если оно есть в списке **и** его можно человеку (бэк-сервис проверяет роль, аудитории, выдачи).

### 10. Привязка к мемориалу
Токен бота действует во всех мемориалах, где человек владелец или модератор (решение 11); если их несколько, бот уточняет в чате, в какой добавлять. Создание мемориала ни к какому мемориалу не привязано.

### 11. Кто может пользоваться ботом
Работать с мемориалом через бота — добавлять посты и файлы — могут только его владелец и модераторы (роли — решение 22а); участники добавляют посты только на сайте. Создать мемориал через бота может любой, кто вошёл (решения 23, 47).

### 12. Срок отзыва
Токен бота живёт 5 минут. Снятие участия или роли срабатывает сразу: бэк-сервис проверяет права по БД на каждом запросе (решение 2). Отвязка Telegram или VK от учётной записи срабатывает для бота с задержкой до 5 минут, пока не истечёт уже выданный токен, — это приемлемо.

### 12а. `ApiToken` не нужен
Убираем `ApiToken` из модели: боту ключ не нужен, он узнаёт человека по аккаунту в Telegram или VK. Вместо `createdByApiTokenId` у каждого изменения хранится канал, через который оно сделано: сайт, бот Telegram, бот VK. Канал — справочник `channel` (решение 51). В истории видно, например, «пост добавила Кира через бота Telegram».

## Роли и права

### 13. Владелец и модераторы
Создатель мемориала — его владелец, владелец у мемориала один. Только он назначает модераторов и снимает их; модераторы этого не могут. Роль владельца можно передать другому человеку — сделаем потом. Что делать, если владельца нет, — вместе с преемственностью (отложено). Роли и их права — решение 22а.

### 14. Автор видит своё
Автор видит то, что создал сам, даже если пост закрыт от его аудиторий, — пока у него есть доступ (решение 43).

### 15. `CONTRIBUTE` и видимость
Добавлять посты можно только в раздел, который человек видит: для добавления нужны и `CONTRIBUTE`, и `VIEW`. Само `CONTRIBUTE` раздел не открывает. Если владелец или модератор выдаёт `CONTRIBUTE` аудитории, которой раздел не открыт, сайт предупреждает: «Друзья не видят этот раздел, добавлять в него они не смогут».

### 16. Оригиналы по умолчанию
Оригинал нового фото скачивается по настройке мемориала, отдельно разрешать не нужно. Пример: на мемориале «Семья может скачивать оригиналы» — Семья сразу скачивает оригинал нового фото. Отдельный файл владелец или модератор может закрыть — флажком «Оригинал закрыт» (решение 39).

### 17. «Всем» — только просмотр
Аудитории «Все» не выдаются `CONTRIBUTE` — ни на мемориал, ни на разделы, — `WRITE_TRIBUTE` и `DOWNLOAD_ORIGINALS` (решение 44): ей можно открыть только просмотр. Без входа не известно, кто написал пост или запись, — путь к спаму; в оригинале бывают координаты съёмки. Публиковать и скачивать оригиналы владелец или модератор разрешает аудиториям участников — например, «Семье» и «Друзьям».

### 18. Памятная книга
Писать в памятной книге может участник из аудитории, которой владелец или модератор выдал право «Писать в памятную книгу» (`WRITE_TRIBUTE`) на мемориал (решение 44), если он видит мемориал. «Всем» это право не выдаётся (решение 17). Кто не участник (например, бывший ученик), написать не может: сначала его приглашают и добавляют в такую аудиторию.

### 19. Видимость людей
- Список участников мемориала видят только владелец и модераторы.
- Состав аудиторий (кто в «Семье», кто в «Друзьях») видят только владелец и модераторы: по нему они решают, кому что открыть; остальным он не нужен, а узнать, что тебя нет в «Семье», бывает обидно.
- Имя и аватар автора поста или записи памятной книги видит каждый, кто видит сам пост или запись.

### 20. Скрытое
Закрытый от человека пост или раздел отвечает «Страница не найдена» (404), а не «Доступ запрещён» (403): иначе видно, что такой объект есть, а по адресу иногда и о чём он. Закрытый мемориал целиком по-прежнему показывает название и кнопку «Запросить доступ» (раздел 8.3 `Access.md`).

## Администратор и создание мемориала

### 21. Права администратора
Администратор платформы видит все мемориалы, может приостановить мемориал (временно не открывается) и скрыть отдельный пост — на случай жалобы или требования закона. Править чужие тексты не может. Удалять мемориал целиком не может: удаление не отменить, решим потом отдельно.

### 22. Роли платформы
Роли и права платформы (для её команды, а не для семей) хранятся в базе бэк-сервиса, вне мемориалов, без `tenant_id`:
- роли и права — строки общих таблиц `role`, `permission`, `role_permission` с пометкой `scope = PLATFORM` (решение 41);
- `platform_role_assignment` — кому выдана роль платформы: человек, роль, кто и когда назначил, когда отозвали.

Код проверяет право по его коду из базы и никогда не проверяет роль; право, на которое в коде никто не ссылается, ничего не открывает. Новая роль — новые записи в базе, без изменения кода.

Сейчас одна роль — «Администратор» с правами из решения 21: видеть все мемориалы, приостановить мемориал, скрыть пост. Модератор платформы (разбирает жалобы, видит только то, на что пожаловались; не путать с модератором мемориала, решение 22а) и поддержка (учётные записи и способы входа, без содержимого мемориалов) — когда появится команда.

### 22а. Роли в мемориале
Роли мемориала и их права хранятся в базе так же, как роли платформы (решение 22): в тех же общих таблицах, с пометкой `scope = MEMORIAL` (решение 41). Одинаковы для всех мемориалов. `Membership.role` становится ссылкой на роль.

| Роль | Права |
|---|---|
| Владелец | один на мемориал — создатель (решение 13); всё, что у модератора, и ещё назначать и снимать модераторов |
| Модератор | видеть всё; приглашать участников; настраивать аудитории, видимость и выдачи прав; скрывать и удалять чужие посты |
| Участник | только то, что выдано его аудиториям: видеть, добавлять посты, писать в памятную книгу, скачивать оригиналы |

«Главного владельца» нет: владелец один, остальные, кто управляет мемориалом, — модераторы. Права ролей по кодам — решение 49, наполнение — решение 50. Полный список прав — [«Все права» в `Access.md`](Access.md#все-права).

### 23. Создание мемориалов
Создать мемориал (кнопкой на сайте или через бота) может любой, кто вошёл через VK или Telegram, — не больше 20 мемориалов на человека. Предел — в настройках, меняется без изменения кода; если кому-то нужно больше, администратор поднимает ему предел.

## Несогласованности

### 24. Аудитории и участие
Состав аудитории ссылается не на человека (`Person`), а на его участие в мемориале (`Membership`): `AudienceMember` → `AudienceMembership` со ссылкой на `membershipId`. Отозвали участие — человек выпадает из всех аудиторий мемориала; при новом приглашении аудитории назначаются заново; в аудиторию нельзя добавить того, кто не участник.

### 25. Аудитории приглашения
Аудитории, в которые попадёт приглашённый, — не список внутри `Invitation` (`audienceIds`), а отдельная таблица «приглашение — аудитория», по строке на аудиторию. Каждая строка — ссылка на аудиторию, за которой следит база: удалили аудиторию — строки приглашений с ней удаляются.

### 26. Отметки окончания
- `grantedByPersonId` и `grantedAt` убираем: они всегда совпадают с `createdByPersonId` и `createdAt` — запись создаётся в момент выдачи.
- У участия (`Membership`) и приглашения (`Invitation`) окончание отмечается только отзывом (`revokedAt`, `revokedByPersonId`); `deletedAt` у них не ставится. В истории видно: «Петя был участником с 1 марта по 28 октября, убрала Аня».

### 27. Уникальность
Правила «двух одинаковых записей быть не может» проверяют только действующие записи — не отозванные и не удалённые: участие (`Membership`), выдачи прав (`AccessGrant`), способы входа (`AuthIdentity`, пара `provider` + `externalId`). Иначе убранного человека нельзя пригласить снова, а отвязанный VK — привязать заново.

### 28. Мелкие противоречия
- Из списка объектов с историей видимости (раздел 8.4 `Main.md`) убираем «контент»: своей видимости у контента нет, он виден тем, кому виден пост.
- Фразу «`Person` — единственная сущность вне тенанта» исправляем: вне мемориалов `Person` и `AuthIdentity` (в сервисе аутентификации, решение 1), профили людей и роли платформы (в бэк-сервисе, решения 34 и 22).

## Чего не хватает

### 29. Журнал безопасности
Журнал безопасности нужен: описываем его в модели и закладываем. Что из него и когда реализовывать, владелец платформы выдаёт по частям.

Черновик описания, уточняется при переносе в модель:
- **что записывается:** входы и выходы, привязка и отвязка способов входа; приглашения, заявки и их решения, выдача и отзыв участия; назначение и снятие ролей мемориала и платформы; изменения аудиторий и выдач прав; действия администратора (приостановка мемориала, скрытие поста);
- **где:** входы и способы входа — в сервисе аутентификации; участие, роли, аудитории, права и действия администратора — в бэк-сервисе;
- **одно событие:** когда, кто (человек), через какой канал (сайт, бот Telegram, бот VK — решение 12а), что произошло, над каким объектом, в каком мемориале.

Учесть: задним числом журнал не восстановить — события, которые не записывались, потеряны.

### 30. Защита от спама
- У человека в одном мемориале может быть только одна нерассмотренная заявка на доступ (`AccessRequest` в статусе `PENDING`); новую можно подать, когда прошлую одобрили или отклонили.
- Ссылка-приглашение по умолчанию действует 7 дней; срок — в настройках. Другой срок или «бессрочно» модератор выбирает сознательно при создании ссылки.

## Второй проход: трудно исправить потом

### 31. Сессии на хостах мемориалов
Обычная схема единого входа — так устроены Google, Keycloak, Auth0; Spring Security и Spring Authorization Server её поддерживают:
- Главный вход хранит сервис аутентификации.
- После входа бэк-сервис получает от сервиса аутентификации пропуск (access token) на 5 минут и ключ продления (refresh token) и хранит их у себя, в сессии мемориала. Браузеру — только номерок: cookie со случайным идентификатором, привязанная к хосту мемориала (раздел 2).
- Пропуск бэк-сервис проверяет сам, по подписи сервиса аутентификации, не обращаясь к нему.
- Активность — запросы человека: открыть страницу, нажать кнопку. Когда пропуск истёк, бэк-сервис на следующем запросе получает новый, а ключ продления каждый раз выдаётся заново на час. Нет запросов час — ключ истекает, нужен вход заново (решение 4). Точность — 5 минут.
- Сервис аутентификации связывает каждый ключ продления с главным входом: «Выйти» закрывает всё сразу, а продление в любом мемориале продлевает и главный вход — в соседний мемориал человек заходит без повторного входа. Эту связь пишем сами, остальное — стандартное.
- «Выйти» срабатывает во всех мемориалах не позже чем через 5 минут. Если понадобится мгновенно — сервис аутентификации сам рассылает мемориалам «выйди».
- Если сервис аутентификации недоступен, вошедшие работают до конца пропуска; войти заново нельзя.
- Реализация: главный вход — сессия Spring Session (стандартная таблица `spring_session`), выданные ключи — стандартная таблица Spring Authorization Server `oauth2_authorization` с нашим столбцом `session_id`. Своей таблицы сессий нет (`Access-schema.md`, раздел 1).
- Не решено: чтение без нажатий час и дольше считается бездействием. Если это неудобно — сайт, пока вкладка открыта, может сообщать бэк-сервису «я здесь».

### 32. Что записано в пропуске
В пропуске — человек и канал (сайт, бот Telegram, бот VK); пропуск сайта и пропуск бота устроены одинаково. Мемориала в пропуске нет: пропуск действует во всей системе, а в каких мемориалах и что человеку можно, бэк-сервис проверяет по базе на каждом запросе (решение 2). Канал записывает сервис аутентификации, когда выдаёт пропуск, — бэк-сервис берёт канал только из пропуска, не со слов браузера или бота. Привязка пропуска к мемориалу почти ничего не защищала: пропуск не уходит из бэк-сервиса в браузер.

### 33. Уровень платформы вне мемориалов
- Адрес платформы — `у-истока.рф`: «Мои мемориалы», «Создать мемориал», профиль и публичный контакт (их хранит бэк-сервис, решение 34).
- Для обычных людей в бэк-сервисе два узких запроса поверх мемориалов: «мемориалы этого человека» — только те, где он участник (с адресами — для перехода и для бота), и «создать мемориал». Всё остальное работает внутри одного мемориала (ADR 0009).
- Администрирование — отдельный вход внутри бэк-сервиса, отгороженный как отдельный сервис: свой адрес `admin.у-истока.рф`; пускает только с правом платформы (решение 22); только у этой части доступ к базе поверх всех мемориалов. Отдельный сервис не заводим: своих данных у администрирования нет, оно меняет данные мемориалов, владелец которых — бэк-сервис. В отдельный сервис выносится только то, у чего появятся свои данные, — например, жалобы; данные мемориалов он меняет через API бэк-сервиса (решение 52).

### 34. Профиль человека — в бэк-сервисе
- Сервис аутентификации владеет тем, как человек входит: номер человека, способы входа (`AuthIdentity`), сессии.
- Бэк-сервис владеет тем, кто человек на платформе: своя таблица профилей — номер человека из сервиса аутентификации, имя, аватар, публичный контакт. Это не копия, а его данные; все ссылки на человека в бэк-сервисе (участие, авторы, служебные поля, журнал) — внешние ключи на неё.
- Профиль создаётся, когда бэк-сервис впервые видит пропуск человека — из любого канала (решение 53); имя и аватар бэк-сервис обновляет при каждом входе — сервис аутентификации отдаёт их вместе с ключами (решение 31). Публичный контакт человек меняет в бэк-сервисе. Имя, изменённое в VK или Telegram, обновится при следующем входе.
- Синхронизации данных между сервисами нет. Бэк-сервису сообщают прямым вызовом только об удалении аккаунта и слиянии учёток (решения 5, 7).
- Открыто вместе с решением 8: может ли бот регистрировать человека, который ни разу не входил на сайт. Профиль в любом случае создаётся при первом пропуске (решение 53).

### 35. Правило видимости — в одном месте
Кто что видит, записано в коде бэк-сервиса один раз — отдельным сервисом (`VisibilityService`, имя уточнить по правилам кода): проверка для одного объекта и условие для списков. Страница поста, лента, поиск, файлы и бот сами ничего не проверяют, а вызывают его. Отдельный сервис-программу для прав (как SpiceDB, OpenFGA) не заводим: ему нужна копия разделов, постов, аудиторий и участников и их сверка при каждом изменении. Одно место в коде при необходимости можно вынести в отдельный сервис. Предупреждение при переносе — открытый вопрос 15 в `Access.md`.

### 36. Роли и права в базе: постоянные коды
- Роли и права — два разных справочника (решения 22 и 22а). У каждой роли и каждого права постоянный код (`OWNER`, `MODERATOR`, `MEMBER`; `VIEW_ALL_MEMORIALS`, `SUSPEND_MEMORIAL`, `HIDE_POST`), название можно менять, код — никогда. Программа ищет роли и права только по коду. У каждой таблицы `id` — `uuid`, все ссылки между таблицами — по `id`; роли и права, о которых знает программа, миграция создаёт с постоянным `id`, одинаковым во всех базах.
- Роли и права, которые знает программа, создаёт миграция, а не правка руками в базе, — они одинаковые во всех базах.
- «Владелец у мемориала один» проверяет сама база: не больше одного действующего участия с ролью `OWNER` на мемориал.

### 37. Бот: защита на стороне бэк-сервиса
- Бэк-сервис сам отклоняет запросы с каналом «бот» (решение 32) на запрещённые боту действия (решение 9): открыть контент другим, поменять аудитории, участников, права и настройки. Одна проверка канала, а не система областей. Ошибка или взлом бота не дают ему прав владельца. Уточнено решением 51: не список запретов, а набор прав канала — всё новое для бота закрыто.
- Бот отвечает только в личных чатах: в групповом чате ответы с закрытыми воспоминаниями увидят все.

## Одно и то же записано двумя способами

### 38. Черновик — один способ
Черновик — объект видят только владелец и модераторы — записывается выдачей `VIEW` системной аудитории «Владелец и модераторы» (код `OWNER_AND_MODERATORS`; прежнее название «Только владельцы», `OWNERS`). Состояния «нет ни одной выдачи `VIEW`» у объекта с настройкой видимости нет. «Владелец и модераторы» не сочетается с другими аудиториями: выбрали любую аудиторию — «Владелец и модераторы» снимается; убрали последнюю — ставится «Владелец и модераторы». Мемориал, раздел и пост владельца или модератора (`MANAGE_CONTENT`, решение 50) создаются с «Владелец и модераторы» (раздел 8.1 `Access.md`).

### 39. Оригиналы отдельного файла — флажок
У файла флажок «Оригинал закрыт». Снят (по умолчанию) — оригинал скачивают те, кому разрешает настройка мемориала (`DOWNLOAD_ORIGINALS` на мемориал). Поставлен — только владелец и модераторы. Выдачи `DOWNLOAD_ORIGINALS` на файл и запись «Все» на каждом новом файле убираем: `DOWNLOAD_ORIGINALS` выдаётся только на мемориал.

### 41. Общие таблицы ролей и прав
Роли, права и права ролей — общие таблицы `role`, `permission`, `role_permission` с пометкой `scope`: `PLATFORM` — платформа, `MEMORIAL` — роли мемориала, `AUDIENCE` — права, которые выдаются аудиториям (`VIEW`, `CONTRIBUTE`, `WRITE_TRIBUTE`, `DOWNLOAD_ORIGINALS`). Права аудиторий ни в одну роль не входят. Подходит ли пометка, проверяет код при записи; технических столбцов с пометкой в таблицах выдачи нет. Тип объекта выдачи — справочник `object_type`. Какое право на какой тип можно выдать — таблица «многие ко многим» `permission_object_type`; `access_grant` ссылается на строку этой таблицы (`permission_object_type_id`), и выдать право на неподходящий тип база не даёт. Таблицы — `Access-schema.md`, разделы 2 и 5. Список прав — [«Все права» в `Access.md`](Access.md#все-права).

### 42. Скрытие по требованию закона
Скрытие поста администратором платформы — отдельная отметка у поста: `item.platform_hidden_at`, кто скрыл (`platform_hidden_by_person_id`) и причина (`platform_hidden_reason`). Владелец и модераторы её не снимают и видят «Скрыто администрацией платформы»; их собственное скрытие постов (решение 22а) — другое и снимается ими. Приостановка мемориала — уже отдельный статус `tenant.status = SUSPENDED`, снять его может только администратор.

## Поправить формулировки

### 43. Автор видит своё — пока есть доступ
Автор видит свои посты и записи памятной книги, пока он участник мемориала: после отзыва участия он гость и видит только открытое «Всем». Писать в памятную книгу могут только участники (решение 44), поэтому правило для постов и записей одно.

### 44. Публикуют только разрешённые аудитории
Публиковать — добавлять посты и писать в памятную книгу — могут только аудитории, которым владелец или модератор выдал право: посты — `CONTRIBUTE` на мемориал или раздел, памятная книга — `WRITE_TRIBUTE` («Писать в памятную книгу») на мемориал. «Всем» эти права не выдаются (решение 17). Например: «Семья» — `CONTRIBUTE` на раздел «Детство» и `WRITE_TRIBUTE`, «Друзья» — только `WRITE_TRIBUTE`. Кто не участник мемориала, не публикует ничего: сначала его приглашают и добавляют в аудиторию.

### 45. Возврат после входа и собственные домены
После входа сервис аутентификации возвращает человека с одноразовым кодом только на поддомены платформы (`vostok.у-истока.рф`) из `tenant_host`. Собственные домены мемориалов (`a-vostok.ru`) пока не поддерживаем: добавить их нельзя. Вернём вместе с проверкой, что домен принадлежит владельцу мемориала и смотрит на наш сервер (`verified_at`), — тогда возвращать и на подтверждённые собственные домены. Иначе злоумышленник добавит к своему мемориалу домен на своём сервере и получит туда человека после входа и его одноразовый код. Открытый вопрос 17 в `Access.md`.

### 46. Правила способов входа
Последний способ входа отвязать нельзя: иначе человек больше не войдёт, а его мемориалы останутся без владельца. Новый способ привязывается только из своей открытой сессии и только входом через него: сессия подтверждает, что это сам человек, вход — что VK или Telegram принадлежит ему. В `auth_identity` появляется ещё одна строка с тем же `person_id`.

### 47. Бот и создание мемориала
Создать мемориал через бота может любой, кто вошёл, — до 20 мемориалов на человека (решение 23); создатель становится владельцем. Работать с мемориалом через бота — добавлять посты и файлы — могут только его владелец и модераторы (решения 10, 11); участник (`MEMBER`) добавляет в этот мемориал только на сайте. Что бот делает с человеком, который ещё не входил на сайт, — отложено (решение 8).

### 48. Персональные данные
Имена и аватары авторов видят все посетители публичного мемориала (решение 19) — это распространение; воспоминания, которые человек пишет боту, уходят языковой модели другой компании (решение 8). По 152-ФЗ:
- Согласия (решение 7) делаем до того, как на платформу придут люди. Их три, каждое — отдельным документом, не пунктом пользовательского соглашения: на обработку данных; на распространение имени, аватара и публичного контакта (ст. 10.1); на передачу воспоминаний языковой модели — бот спрашивает его перед первой обработкой.
- Каждое согласие — отдельная запись: какое, на какую версию документа, когда дано, когда отозвано.
- Языковая модель для ботов — у российского поставщика по API (например, GigaChat), с договором поручения обработки (ст. 6 ч. 3). Своей модели на своём сервере пока нет.
- С юристом до запуска: тексты согласий; что видят посетители, если человек не дал согласия на распространение; данные самих умерших — по ст. 9 ч. 7 согласие за умершего дают наследники (норму сверить).

## Третий проход: что аукнется потом

### 49. Права вместо проверок ролей
Код проверяет только права (решение 22), поэтому у каждого правила вида «владелец и модераторы могут…» — своё право, а роль — только набор прав в `role_permission`. Кому что — строки `role_permission`: меняются без изменения кода. Недостающие права:

| Правило | Право | Кому сейчас |
|---|---|---|
| Скачивать любые оригиналы — закрытые и без выдач (решение 39) | `DOWNLOAD_ALL_ORIGINALS` | владелец, модератор |
| Одобрять заявки на доступ | `APPROVE_REQUESTS` | владелец |
| Убирать участников | `REMOVE_MEMBERS` | владелец |
| Настройки мемориала: показ поисковикам | `MANAGE_SETTINGS` | владелец |
| Скрывать записи памятной книги | `MODERATE_TRIBUTES` | владелец |
| Поднять человеку предел мемориалов (решение 23) | `RAISE_MEMORIAL_LIMIT`, право платформы | администратор |

На существующие права ложатся: список участников и состав аудиторий (решение 19) и флажок «Оригинал закрыт» (решение 16) — `MANAGE_AUDIENCES`; заметки приглашений — `INVITE`. Наполнение — решение 50, бот — решение 51. Полный список прав — [«Все права» в `Access.md`](Access.md#все-права).

Исключения:
- роль владельца — структура мемориала: на `OWNER` опираются только правила «владелец один», «хранитель — владелец» и передача роли;
- «Владелец и модераторы» (`OWNER_AND_MODERATORS`) — пометка черновика: её состав не вычисляется по ролям, черновик видят те, у кого `VIEW_ALL`.

### 50. Наполнение мемориала
Наполнять мемориал может тот, у кого право `MANAGE_CONTENT`: владелец и модератор. Оно даёт добавлять, менять и удалять разделы, людей мемориала и оформление, добавлять посты и менять и удалять свои. Чужие посты не правят: владелец и модераторы их скрывают и удаляют (`MODERATE_POSTS`, решение 22а). У участников этого права нет — посты они добавляют по `CONTRIBUTE` в открытые им разделы (решения 15, 44). Через бота `MANAGE_CONTENT` действует (решение 51).

Пост, добавленный по `MANAGE_CONTENT`, — владельцем, модератором или через бота — создаётся черновиком («Владелец и модераторы», решение 38); пост по `CONTRIBUTE` сразу виден «Всем». Открыть пост бот не может (решение 9) — его открывают на сайте.

### 51. Бот: набор прав канала
Канал — справочник `channel`: `SITE`, `TELEGRAM_BOT`, `VK_BOT`. Какие права действуют через канал — таблица `channel_permission` «канал — право», устроенная как `role_permission`; строки создаёт миграция. Действие проходит, только если право есть и у человека (роль, аудитории), и в наборе канала из пропуска.
- Сайту выданы все права.
- Каналам ботов — только права ролей мемориала, нужные для действий из решения 9: `VIEW_ALL`, `MANAGE_CONTENT` (решение 50), `DOWNLOAD_ALL_ORIGINALS`. Прав аудиторий в наборе ботов нет, поэтому участник через бота с мемориалом не работает — решения 10 и 11 выполняются сами.
- Новое право сайту выдаёт та же миграция, что его создаёт; ботам — только отдельным решением: всё новое для бота закрыто. Это заменяет список запрещённых боту действий из решения 37.
- Не через права: менять и удалять бот может только созданное через бота (решение 9); создать мемориал может любой, кто вошёл (решение 47).
- Служебные поля `created_via_channel_id`, `updated_via_channel_id` ссылаются на `channel.id`. Новый мессенджер — новая строка в `channel` и строки его прав.

Список инструментов языковой модели живёт в коде приложения бота и только помогает модели; защищает набор прав канала в бэк-сервисе.

### 52. Изоляция мемориалов и запросы поверх них
Изоляция мемориалов в базе (RLS, ADR 0009) остаётся: обычный запрос видит только свой мемориал, даже если в коде забыт фильтр. Поверх мемориалов работают только три вещи, и у каждой свой узкий путь:
- «Мои мемориалы» и «создать мемориал» (проверка предела, решение 23) — узкие функции базы, которые отдают только данные этого человека, а не доступ ко всему;
- администрирование — своя роль базы с доступом ко всем мемориалам; обычные запросы под ней не ходят.

Администрирование — отдельный модуль бэк-сервиса: адрес `admin.у-истока.рф`, права платформы, своя роль базы. В отдельный сервис не выносим: своих данных у администрирования нет, оно меняет данные мемориалов, а их владелец — бэк-сервис. Отдельным сервисом становится только то, у чего появятся свои данные, — например, жалобы (сервис модерации); данные мемориалов он меняет через API бэк-сервиса, без доступа к его базе.

### 53. Когда создаётся профиль
Профиль создаётся в одном месте — когда бэк-сервис впервые видит пропуск человека, из любого канала, — а не в сценарии входа на сайт. Имя и аватар бэк-сервис берёт у сервиса аутентификации, как при входе (решение 34). Так любой новый путь, которым человек может прийти, — бот, другой мессенджер, приложение — работает без своего кода создания профиля, а записи от имени человека всегда могут сослаться на его профиль. Может ли бот регистрировать человека, который ещё не входил на сайт, — по-прежнему открыто (решение 8); правило работает при любом ответе.

### 54. Удаление аудитории
Свою аудиторию удаляют в одной транзакции вместе со всем, что с ней связано: её выдачами (`AccessGrant`), составом (`AudienceMembership`) и строками приглашений (`InvitationAudience`, решение 25). Объект, у которого это была последняя выдача `VIEW`, становится черновиком — получает «Владелец и модераторы» (решение 38), а не остаётся невидимым для всех. Системные аудитории не удаляются. Внешнего ключа на объект выдачи нет, поэтому при записи выдачи код проверяет `objectId`: объект из того же мемориала и того типа, что в паре `PermissionObjectType`.
