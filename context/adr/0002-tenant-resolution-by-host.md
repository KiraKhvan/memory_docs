# ADR-0002: Резолвинг тенанта по `Host`-заголовку

## Статус

Принято, 2026-07-30

## Контекст

ADR-0001 зафиксировал мультитенантность через общую БД с дискриминатором `tenant_id`. Открытым остался вопрос: откуда приложение узнаёт, к какому тенанту относится входящий запрос.

Обстоятельства:

- Домен платформы: `ochag.family`. Мемориалы по умолчанию получают поддомен `<имя>.ochag.family`
- Первый мемориал (сайт памяти отца) с самого начала работает на кастомном домене `a-vostok.ru` — то есть механизм должен поддерживать оба случая уже в v1
- Ссылку на мемориал родственник получает напрямую (в мессенджере, по телефону), органический поиск не основной канал
- ADR-0001 требует: `tenant_id` никогда не принимается от клиента

## Рассматривавшиеся варианты

**1. Путь в URL** — `ochag.family/memorial/1` или `/m/vostok`
**2. Поддомен** — `vostok.ochag.family`
**3. Кастомный домен** — `a-vostok.ru`
**4. Явный параметр или заголовок** — `?tenantId=1`, `X-Tenant-Id`

## Решение

Тенант определяется **по значению `Host`-заголовка входящего запроса**. Поддержаны варианты 2 и 3 одним механизмом: в таблице тенантов хранится список привязанных хостов, резолвер ищет точное совпадение.

Вариант 1 отклонён по продуктовым причинам: для родственника ссылка `a-vostok.ru` или `vostok.ochag.family` ощущается как отдельный сайт, а `ochag.family/memorial/1` — как страница внутри чужого сервиса. Для мемориального продукта это не косметика. Дополнительно: переезд мемориала на собственный домен при путевой схеме означает смену всех URL, при хостовой — смену DNS-записи.

Вариант 4 отклонён как нарушающий ADR-0001: `tenant_id`, приходящий от клиента, обнуляет изоляцию. Это самая частая уязвимость мультитенантных систем — параметр добавляют «на время», ради одного удобного сценария, и он остаётся.

## Последствия

### Положительные

- Поддомены и кастомные домены обрабатываются единым кодом — подключение кастомного домена не требует изменений в приложении
- Тенант известен до контроллера: авторизация, фильтрация ORM и логирование получают его из контекста
- Клиент не может влиять на выбор тенанта

### Отрицательные и требующие компенсации

- **Cookie и сессии нельзя привязывать к родительскому домену.** Cookie, выставленная на `.ochag.family`, будет отправляться на все поддомены — то есть сессия одного мемориала утечёт в другой. Cookie выставляются строго на конкретный хост, без ведущей точки. Это следствие легко упустить: конфигурация по умолчанию в ряде фреймворков ведёт себя иначе
- **Локальная разработка усложняется** — `localhost` не даёт поддоменов из коробки. Решение: `*.localhost` (поддерживается современными браузерами) либо wildcard-DNS-сервисы вида `lvh.me`. Заголовок-override для удобства разработки допустим только при активном dev-профиле и должен физически отсутствовать в prod-сборке
- **Операционные расходы на домены.** Wildcard-сертификат `*.ochag.family` покрывает поддомены; каждый кастомный домен требует отдельного сертификата. В v1 — вручную для `a-vostok.ru`; автоматизация (Let's Encrypt с DNS-challenge) в v1.1
- **Неизвестный хост требует явной обработки** — запрос на непривязанный домен должен возвращать нейтральную страницу, а не падать и не отдавать какой-то тенант по умолчанию
- **Кросс-доменные вызовы.** Веб-клиент и API должны быть на одном хосте тенанта (через reverse proxy), иначе появляется CORS и усложняется передача cookie

## Реализация

1. Таблица `tenant_hosts` (`host`, `tenant_id`, `is_primary`) — один тенант может иметь несколько хостов (поддомен платформы + кастомный домен). Один из них помечен основным для генерации абсолютных ссылок
2. Servlet-фильтр максимально рано в цепочке: нормализация хоста (нижний регистр, отбрасывание порта), поиск тенанта, помещение в request-scoped контекст, из которого его берёт ORM-фильтр
3. Кэширование карты «хост → тенант» в памяти с инвалидацией при изменении — резолвинг происходит на каждом запросе, обращение к БД за ним избыточно
4. Хост не найден — отдельная нейтральная страница платформы, никаких fallback-тенантов
5. Редирект с неосновных хостов на основной — по решению владельца мемориала, не по умолчанию
6. Cookie/сессия: `Domain` не задаётся, привязка к конкретному хосту
7. Автотест: запрос с хостом тенанта A не возвращает данные тенанта B (дополняет тест изоляции из ADR-0001)

## Связанные решения

- ADR-0001: мультитенантность через общую БД с `tenant_id`
