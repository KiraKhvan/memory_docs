# ADR-0003: Фасетная разметка контролируемым словарём

## Статус

Принято, 2026-07-30

## Контекст

Полнотекстовый поиск перенесён в v1.1 (см. scope 5.2). В v1 навигация по архиву обеспечивается фильтрацией и группировкой — то есть вся нагрузка по поиску нужного материала ложится на систему разметки.

Разметка относится к решениям, которые дорого пересматривать: она применяется ко всему объёму контента сразу, и её переделка означает повторный проход по всему архиву. Поэтому механизм разметки фиксируется до наполнения, даже если конкретный состав разметки ещё не определён.

Обстоятельства:

- Архив размечается один раз ограниченным кругом людей, а не массово пользователями
- Разные типы контента размечаются разными измерениями: у стихотворения нет места съёмки, у фотографии нет стихотворной формы
- Часть измерений сквозная — период жизни осмысленно фильтровать через все разделы сразу
- Платформа мультитенантная: словарь одной семьи не применим к другой

## Рассматривавшиеся варианты

**1. Свободные теги** — произвольная строка при разметке
**2. Плоский контролируемый словарь** — единый заранее определённый список
**3. Фасетный контролируемый словарь** — теги сгруппированы в независимые измерения

## Решение

Принят **вариант 3: фасетная разметка контролируемым словарём**.

Вариант 1 отклонён: без нормализации словарь расходится вариантами написания одного понятия, и фильтр, на который в v1 возложена вся навигация, перестаёт работать. Массовость разметки, которая в других продуктах компенсирует этот шум, здесь отсутствует.

Вариант 2 отклонён: плоский список не позволяет строить комбинированные фильтры осмысленно — измерения смешиваются в одном перечне, и пользователь не понимает, что с чем сочетается. Для замены поиска фильтрацией этого недостаточно.

**Что решением не определяется:** конкретный состав фасетов, их значения и правила именования. Это отдельная работа, выполняемая до наполнения архива, но не блокирующая проектирование модели данных и API.

## Следствия для модели данных

1. **Тег — сущность, а не строка в поле контента.** Поля: идентификатор, отображаемое имя, фасет, `tenant_id`, применимость к типам контента
2. **Фасет — сущность.** Поля: идентификатор, имя, признак единственности значения (период — одно, тема — несколько), применимость к типам контента, порядок отображения
3. **Словарь принадлежит тенанту.** У каждого мемориала свой набор фасетов и значений
4. Фасеты делятся на сквозные (применимы ко всем типам контента) и специфичные для типа
5. Связь контента с тегами — many-to-many, с соблюдением ограничения единственности там, где фасет её требует

## Последствия

### Положительные

- Фильтры строятся из справочника, а не из `SELECT DISTINCT` по контенту
- Переименование тега не требует изменения размеченных записей
- Дубликаты с другим регистром или числом структурно невозможны
- Комбинированная фильтрация по нескольким измерениям выражается естественно
- При появлении поиска в v1.1 фасеты становятся фильтрами поисковой выдачи, а не вытесняются ею

### Отрицательные и требующие компенсации

- Нужен интерфейс управления словарём — в v1 минимальный, в рамках админ-панели
- **Порядок работ жёстче:** словарь определяется до массовой разметки, а не по ходу. Пополнение словаря на лету при разметке фактически превращает его в свободные теги, поэтому право пополнения ограничивается владельцем
- Разметка становится более трудоёмкой, чем ввод произвольной строки
- Новому тенанту нужен стартовый словарь — иначе разметка начинается с пустого списка. Шаблон словаря по умолчанию: не в v1, но предусмотреть при переходе к продаже

## Путь отхода

Свободные теги при необходимости добавляются поверх как отдельный фасет «прочее» без контроля значений — обратный переход (от свободных к контролируемым) потребовал бы ручной нормализации всего архива, поэтому выбранный порядок односторонне безопасен.

## Связанные решения

- ADR-0001: мультитенантность через общую БД с `tenant_id` — словарь тенант-скоупный
- Scope 5.2: перенос полнотекстового поиска в v1.1 — причина, по которой разметка критична в v1
