# ADR-0001: Мультитенантность через общую БД с дискриминатором `tenant_id`

## Статус

Принято, 2026-07-30

## Контекст

Платформа изначально проектируется как мультитенантная: первый мемориал (сайт памяти отца) — это тенант №1, в дальнейшем предполагается продажа решения другим семьям. Решение о модели изоляции данных нужно принять до первой миграции, поскольку retrofit тенантности в существующую схему требует переписывания всех запросов, эндпоинтов и проверок доступа.

Существенные обстоятельства:

- Контент чувствительный (закрытые семейные материалы), но не подпадает под регуляторные требования к физической изоляции — нет платёжных, медицинских или иных специально регулируемых данных
- Ожидаемая нагрузка на тенант невелика: до 50 одновременных посетителей, пики в памятные даты
- Требование NFR: стоимость простаивающего мемориала должна сводиться к стоимости объектного хранилища, без постоянного рантайма на тенант
- Команда — 1,5 разработчика, целевая дата первого релиза — сентябрь 2026
- Бюджет на инфраструктуру ограничен, проект пока некоммерческий

## Рассматривавшиеся варианты

**1. Общая БД, общая схема, дискриминатор `tenant_id`**
Все тенанты в одних таблицах, разделение по колонке.

**2. Схема на тенанта**
Одна БД, отдельная схема PostgreSQL под каждого тенанта.

**3. БД на тенанта**
Отдельная база данных под каждого тенанта.

## Решение

Выбран **вариант 1: общая БД с дискриминатором `tenant_id`**.

Варианты 2 и 3 отклонены: они дают более сильную изоляцию, которая в данной предметной области не требуется, но при этом кратно усложняют миграции (набор миграций надо применять к каждой схеме/базе), провижининг нового тенанта, мониторинг и бэкапы. При команде 1,5 человека и сроке в два месяца эта сложность несовместима с релизом. Дополнительно вариант 3 нарушает требование по стоимости простаивающего тенанта — отдельная БД потребляет ресурсы независимо от активности.

## Последствия

### Положительные

- Один набор миграций на всю платформу
- Создание тенанта — вставка строки, не провижининг инфраструктуры
- Простаивающий тенант не потребляет ресурсов помимо хранилища — соответствует NFR по стоимости
- Один пул соединений, один инстанс приложения, простой мониторинг
- Кросс-тенантная аналитика (сколько мемориалов, сколько контента) — обычный SQL-запрос

### Отрицательные и требующие компенсации

- **Изоляция только логическая.** Ошибка в одном запросе — утечка данных между тенантами. Для мемориального продукта это репутационно фатально: посторонний увидит закрытые семейные материалы чужой семьи. Требует автоматического, а не дисциплинарного контроля (см. «Реализация»)
- **Восстановление одного тенанта усложнено.** Нельзя просто восстановить файл базы: нужна выборочная выгрузка данных тенанта из бэкапа. Требует отдельного отработанного скрипта — не откладывать до первого инцидента
- **Noisy neighbour.** Тяжёлый тенант влияет на остальных. При текущих нагрузках не проблема; при появлении крупного клиента — повод пересмотреть
- Все составные индексы должны начинаться с `tenant_id`, иначе запросы будут сканировать данные всех тенантов

## Реализация

Обязательные к соблюдению следствия решения:

1. **`tenant_id` в каждой таблице**, включая связующие. Исключений нет
2. **Автоматическая фильтрация на уровне ORM** (Hibernate `@Filter` / `@TenantId`), включаемая по умолчанию. Разработчик не должен *помнить* про фильтрацию — он не должен иметь возможности её пропустить
3. **Резолвинг тенанта из `Host`-заголовка** в фильтре до контроллера, помещение в request-scoped контекст. Поддомен и кастомный домен обрабатываются одним механизмом
4. **`tenant_id` никогда не принимается от клиента** — ни в теле запроса, ни в параметре, ни в JWT-claim без проверки. Только из резолвинга по хосту
5. **Составные индексы ведут с `tenant_id`**: `(tenant_id, created_at)`, `(tenant_id, visibility)` и т.д.
6. **Обязательный автотест изоляции**: создать двух тенантов, из-под второго попытаться получить данные первого по прямым идентификаторам, ожидать 404, а не 403 (существование чужого ресурса не должно подтверждаться). Тест — часть Definition of Done для любого нового эндпоинта

## Путь отхода

Если появится клиент с требованием физической изоляции, вариант 3 можно применить точечно к нему одному: резолвинг тенанта уже абстрагирован, поэтому маршрутизация части тенантов в отдельные БД добавляется без изменения бизнес-логики. Гибридная схема (большинство в общей БД, отдельные клиенты в своих) — стандартная эволюция этого решения.

Полный переход всей платформы на схему-на-тенанта — дорогая миграция, к которой это решение осознанно не готовится.
