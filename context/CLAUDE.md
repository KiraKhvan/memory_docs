# Проект «Очаг» — контекст для Claude Code

Мультитенантная платформа мемориальных сайтов. Первый мемориал — сайт памяти отца — создаётся как первый экземпляр платформы, а не как разовый проект.

Подробные документы: `/docs/scope.md`, `/docs/domain-model.md`, `/docs/adr/`.
Этот файл — сводка принятых решений. При расхождении с документами в `/docs/` — правы документы.

---

## 1. Стек

| Слой | Технология |
|---|---|
| Backend | Spring Boot, Java 25 (LTS) |
| БД | PostgreSQL |
| Миграции | Flyway или Liquibase, с первого коммита |
| Контракт API | OpenAPI, подход API-first |
| Веб-клиент | Next.js (React) |
| Медиа | S3-совместимое хранилище |
| Мобильный клиент | v2, только Android, Kotlin + Jetpack Compose. Не в v1 |

Репозитории раздельные: `memorial-backend`, `memorial-web`. Спека OpenAPI лежит в backend-репозитории (`/api/openapi.yaml`), клиенты копируют её при сборке.

## 2. Архитектурные решения (ADR)

### ADR-0001. Мультитенантность: общая БД, дискриминатор `tenant_id`

- `tenant_id` в **каждой** таблице, включая связующие
- Автоматическая фильтрация на уровне ORM (Hibernate `@Filter` / `@TenantId`), включена по умолчанию. Разработчик не должен *помнить* про фильтрацию — он не должен иметь возможности её пропустить
- **`tenant_id` никогда не принимается от клиента** — ни в теле, ни в параметре, ни в claim. Только из резолвинга по хосту. Это самая частая уязвимость мультитенантных систем
- Составные индексы **ведут с `tenant_id`**: `(tenant_id, created_at)`, `(tenant_id, visibility)`
- Обязательный автотест изоляции: создать двух тенантов, из-под второго запросить данные первого по прямым идентификаторам, ожидать **404, не 403** (существование чужого ресурса не подтверждается). Тест — часть Definition of Done для каждого нового эндпоинта
- Отклонены: схема на тенанта, БД на тенанта — избыточная изоляция при кратном усложнении миграций и провижининга

### ADR-0002. Резолвинг тенанта по `Host`-заголовку

- Таблица `tenant_hosts` (`host`, `tenant_id`, `is_primary`): один тенант — несколько хостов
- Servlet-фильтр максимально рано в цепочке: нормализация хоста (нижний регистр, отбрасывание порта) → поиск тенанта → request-scoped контекст, из которого его берёт ORM-фильтр
- Карта «хост → тенант» кэшируется в памяти с инвалидацией при изменении
- **Хост не найден — нейтральная страница платформы. Никаких fallback-тенантов**, даже для отладки
- **Cookie и сессия привязываются к конкретному хосту.** `Domain` не задаётся. Cookie на `.ochag.family` утечёт между поддоменами и обнулит изоляцию
- Веб-клиент и API — на одном хосте тенанта через reverse proxy, иначе CORS и проблемы с cookie
- Локальная разработка: `*.localhost` или `lvh.me`. Заголовок-override допустим **только** при активном dev-профиле и физически отсутствует в prod-сборке
- Отклонены: путь в URL (`/memorial/1` ощущается как страница в чужом сервисе), явный параметр (нарушает ADR-0001)

### ADR-0003. Фасетная разметка контролируемым словарём

- Теги сгруппированы в независимые измерения (фасеты), а не в плоский список
- Словарь принадлежит тенанту: у каждого мемориала свой набор фасетов и значений
- Свободный ввод не допускается. Право пополнять словарь — только у владельца; пополнение на лету при разметке превращает контролируемый словарь в свободные теги
- Причина критичности: полнотекстовый поиск перенесён в v1.1, вся навигация в v1 держится на фильтрации

## 3. Домены

| Уровень | Схема |
|---|---|
| Платформа | `ochag.family` |
| Мемориал по умолчанию | `<имя>.ochag.family`, wildcard-сертификат `*.ochag.family` |
| Первый мемориал | `a-vostok.ru`, настраивается вручную |

Резолвинг по `Host` нужен **в v1**: первый мемориал сразу на кастомном домене. К v1.1 отнесены только автовыдача сертификатов и UI подключения доменов.

## 4. Доменная модель — ключевое

Полностью: `/docs/domain-model.md`.

**Сущности:** `Tenant`, `TenantHost`, `Subject`, `Person`, `AuthIdentity`, `Membership`, `AccessRequest`, `Section`, `ContentItem`, `MediaAsset`, `MediaVariant`, `Facet`, `Tag`, `ContentItemTag`, `FieldProvenance`, `VisibilityDecision`, `Tribute`.

Существенное:

- **`Person` и `AuthIdentity` — вне тенанта.** Сознательное исключение из ADR-0001: человек может быть родственником в нескольких мемориалах. Права даёт только `Membership`, он тенант-скоупный; сама `Person` не даёт прав нигде
- **`Subject`** — человек, которому посвящён мемориал. Связь с `Tenant` **один к одному** (уникальность `tenant_id`). Вынесен отдельной сущностью, несмотря на 1:1: разные ответственности
- **`ContentItem`** — общий тип для всех разделов. Наследование в БД **joined**: таблица общих полей + таблицы специфичных. Типы: `POEM`, `PHOTO`, `BLOG_ENTRY`, `AUDIO`, `VIDEO`
- **`Section`** — сущность, а не константы в коде. Два фотораздела («снимал он» / «снят он») различаются принадлежностью к разделу, а не типом
- **Роль `GUEST` в модели отсутствует** — гость это отсутствие `Membership`, а не запись о нём
- **`MediaVariant.kind = ORIGINAL` не удаляется никогда.** Производные (`WEB`, `THUMBNAIL`, `POSTER`) пересоздаваемы

### Датировка

Даты в семейном архиве часто неточны. Единственное поле `date` вынуждает либо выдумывать точность, либо терять известное приближение. Структура: `dateFrom`, `dateTo`, `precision` (`DAY` / `MONTH` / `YEAR` / `DECADE` / `UNKNOWN`), `displayText`. Фильтрация по периоду — по пересечению интервалов.

### Происхождение метаданных

Две **независимые** оси, не одно поле:

- **Источник**: `TECHNICAL` / `KNOWN` / `INFERRED` / `IMPORTED` / `GENERATED`
- **Подтверждение**: `confirmedByPersonId`, `confirmedAt`. Не выводится из источника — автоматически проставленное значение может быть подтверждено человеком и остаться при этом с источником `GENERATED`

Хранение: `FieldProvenance` для полей `ContentItem` (`fieldName` — строка, новые поля не требуют миграции); для тегов — колонки прямо в `ContentItemTag`. Два механизма вместо одного универсального: полиморфная ссылка ломает внешние ключи.

Отсутствие записи = «происхождение неизвестно». Это допустимое состояние, не ошибка.

Причина: в семейном архиве проверить значение спустя годы будет не у кого. Через двадцать лет предположение станет фактом просто потому, что записано.

### Видимость

`PUBLIC` / `FAMILY` / `DRAFT`. **Дефолт при создании — `DRAFT`**: публикация всегда осознанное действие.

Решение о видимости фиксируется как **событие** (`VisibilityDecision`: кто, когда, с чего на что), а не как перезапись поля. Текущее значение денормализовано в `ContentItem.visibility` для скорости выборок. Механизм согласования между родственниками (поздние релизы) надстраивается поверх истории; поверх одного поля — нет.

Непубличные медиа отдаются **временными ссылками** после проверки роли. Бакет приватный, прямой доступ по URL невозможен. Для длинных аудиозаписей — срок с запасом либо обновление ссылки в процессе воспроизведения.

## 5. Границы первого релиза (сентябрь 2026)

**Входит:** мультитенантность и резолвинг по хосту; пять разделов контента (стихи, фото автора, фото с ним, блог, аудио); просмотр с пагинацией; фасетная фильтрация; админ-панель (CRUD, видимость, словарь тегов); авторизация VK + Telegram; роли и уровни видимости; памятная книга; ручное подтверждение роли родственника; бэкапы; dev-стенд.

**Не входит:** полнотекстовый поиск (v1.1, первый кандидат); видео; мобильное приложение (v2); iOS (v3); биллинг и тарифы; self-serve регистрация тенантов; автовыдача SSL кастомным доменам; согласование публичности родственниками; комментарии к отдельным записям; автомодерация; многоязычность; уведомления; кастомизация оформления клиентом.

**Вне рамок продукта совсем:** физическая изоляция данных тенантов; постоянно работающие ресурсы на каждый тенант.

**Приложение не обрабатывает медиа.** Производные версии фотографий и воспроизводимые версии аудио готовятся вне системы. Фоновая обработка, очереди и воркеры в архитектуре v1 не появляются.

Расшифровки аудиозаписей не ведутся. Поиск по записям — по `title` и `description`.

## 6. Нефункциональные требования

| Категория | Требование |
|---|---|
| Нагрузка | До 50 одновременных посетителей на мемориал |
| Скорость | Первая отрисовка страницы раздела < 2с на мобильном 4G |
| Объём | До ~1000 фотографий и сотен текстов на тенант; без деградации до ~10 000 единиц |
| Доступность | 99%, простой до нескольких часов допустим |
| Изоляция тенантов | Данные одного тенанта недоступны другому ни при каком запросе. **Проверяется автотестами, а не ревью** |
| Сохранность | Ежедневный бэкап БД и медиа, копии ≥ 30 дней. **Оригиналы медиа не удаляются никогда** |
| Стоимость | Простаивающий мемориал стоит только объектного хранилища |
| Расширяемость | Новый тип контента, новый провайдер авторизации, новый тенант не требуют переработки API и клиентов |

### Хранение медиа

Наиболее вероятная причина потери архива — не отказ провайдера, а массовая операция, выполненная ошибочно, либо потеря доступа к аккаунту.

- Версионирование бакета **включено**
- Права на запись и на удаление **разделены**: учётные данные для наполнения не имеют права удаления на бакет с оригиналами
- Правило 3-2-1: рабочая копия / отключённый внешний носитель / хранилище платформы
- Скрипт выборочного восстановления одного тенанта из бэкапа общей БД — написать **до** появления второго тенанта. С общей БД «просто восстановить бэкап» невозможно, это откатит всех

## 7. Конвенции

- **Package by feature**, не по слоям: `poems/`, `photos/`, `auth/`, `tenancy/` — внутри каждого свои controller/service/repository. Не `controllers/`, `services/`, `repositories/`
- **Версионирование API в URL**: `/api/v1/...`. Удаление или переименование поля в ответе — major. У родственников будут старые версии клиента, которые никто не обновит
- **API-first**: спека пишется первой, из неё генерируются интерфейсы контроллеров и клиенты. Не наоборот
- **Абстракции, заложенные ради расширяемости**: `AuthProvider` (VK, Telegram), `MediaStorage` (смена провайдера хранилища)
- Conventional Commits, branch protection на `main`, минимум 1 апрув, ktlint/Checkstyle, `.editorconfig`
- CI на каждый PR: сборка, тесты, линтинг
- Вся документация — **в репозитории**, не в Notion. Расходится с кодом в первую же неделю

### Definition of Done

Код написан → тесты (включая тест изоляции тенантов для новых эндпоинтов) → ревью пройдено → документация обновлена → задеплоено на dev.

## 9. Открытые вопросы

| # | Вопрос | Блокирует |
|---|---|---|
| 1 | **Темы внутри разделов — структура или разметка?** Если «О путешествиях» должна быть страницей с собственным адресом — нужны вложенные разделы (`parentSectionId`). Если это способ сгруппировать список — хватит фасетов из ADR-0003. Влияет на модель | Модель `Section` |
| 2 | Настройки представления раздела: `layout` (`LIST` / `GRID` / `CONTINUOUS`), `defaultOrdering` (`MANUAL` / `DATE_ASC` / `DATE_DESC` / `TITLE`), `groupByFacetId`. Предложены, не утверждены | Модель `Section` |
| 3 | `slug` у `ContentItem` для человекочитаемых URL (`/poems/vecher-na-altae` вместо `/poems/1471`). В модели сейчас нет | Модель `ContentItem`, роутинг |
| 4 | Конкретный состав фасетов и их значения. Механизм зафиксирован, состав — нет | Наполнение, не разработку |
| 5 | Товарный знак «Очаг»: проверить ФИПС по классам 42 и 45 | Ничего. Влияет на защиту бренда при продажах |

## 10. Чего делать не надо

- Не строить SaaS-обвязку: биллинг, тарифы, self-serve онбординг, панель управления тенантами. Тенанты создаются вставкой в БД. Биллинг появляется с третьим платящим клиентом
- Не добавлять фоновую обработку медиа, очереди, воркеры
- Не заводить Elasticsearch. Когда дойдёт до поиска (v1.1) — полнотекстовый поиск PostgreSQL
- Не делать микросервисы. Монолит, слоистая архитектура
- Не принимать `tenant_id` от клиента ни в каком виде
- Не оставлять fallback-тенанта для неизвестного хоста
- Не выставлять cookie на родительский домен
