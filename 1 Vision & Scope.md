# Vision & Scope: Платформа памяти «Очаг»

**Версия:** 0.4 (черновик, не согласован)
**Дата:** 2026-07-30
**Статус:** на обсуждение с командой

---

## 1. Problem Statement / Описание проблемы

Творческое наследие человека — стихи, фотографии, записи в блоге — разрознено: 
часть в бумажном виде, часть в личных архивах, часть на платформах, которые могут закрыться. 
Нет единого места, где это собрано, доступно родным и защищено от исчезновения.

Воспоминания о человеке живут в разговорах и не фиксируются нигде.

Существующие решения — соцсети и конструкторы сайтов — либо не дают контроля над контентом, 
либо не приспособлены к структуре творческого архива.

Нет ни одного решения, которое было бы удобно для долгосрочного использования.
Например: нет возможности авторизации через соц сети. 
Нет приложений для удобного просмотра страниц. 
Через мобильное приложение просматривать такие страницы неудобно. 
А большая часть пользователей сидит в сети через телефоны.

---

## 2. Vision Statement | Ради чего мы это делаем?

**Для** семей, желающих сохранить наследие близкого человека,
**которым нужно** место, где архив собран целиком, доступен родным и переживёт их самих,
**«Очаг»** — это мультитенантный сервис мемориальных сайтов,
**который** объединяет творческое наследие человека с воспоминаниями близких о нём, с гибким управлением приватностью.

**В отличие от** соцсетей и конструкторов сайтов,
**платформа** спроектирована под структуру творческого архива, 
даёт семье контроль над публичностью каждой единицы контента и рассчитана на десятилетия хранения.

**Первый мемориал** — сайт памяти отца — создаётся как первый экземпляр платформы, а не как разовый проект.

### 2.1 Принципы продукта

Утверждения, по которым проверяются решения о функциональности:

- Контент принадлежит семье, а не платформе
- Публичность каждой единицы контента — осознанное решение владельца, а не настройка по умолчанию
- Архив должен пережить платформу: данные экспортируемы, оригиналы не удаляются
- Простаивающий мемориал не должен стоить дорого — иначе его нельзя хранить десятилетиями

## 3. Цели и критерии успеха

**Целевая дата первого релиза: сентябрь 2026.**

**Критерии успеха первого релиза:**
- Первый мемориал доступен по постоянному адресу, работает на телефонах и десктопе
- Четыре раздела созданы, наполнены значимой частью архива (не обязательно всем)

- Настроено и проверено резервное копирование
- **Архитектурно возможно создать второй мемориал без изменения кода** (даже если создание пока ручное)

## 4. Аудитория и сегменты

### 4.1 Аудитория первого мемориала

Родные, друзья и знакомые автора; люди, интересующиеся его творчеством. 
Круг ограничен, состав известен заранее, приход на сайт — по прямой ссылке, а не из поиска.

### 4.2 Сегменты платформы

Сегменты различаются мотивом обращения и способом принятия решения, а не правами в системе. 
В коде первые два неразличимы — оба являются владельцами мемориала, — но требуют разного продукта.

| Сегмент | Мотив | Что для него критично |
|---|---|---|
| **Семья с техническим человеком** | Один человек в семье берёт на себя сохранение архива | Контроль приватности, экспорт данных, гибкость разметки |
| **Семья без технического человека** | Та же потребность, нет ресурса на разметку и настройку | Простой онбординг, помощь с наполнением, готовые словари |
| **Ритуальное агентство** | Канал, а не конечный пользователь: создаёт мемориалы клиентам | Массовое создание, брендирование, оплата от агентства |
| **Наследие вне семьи** | Литературные общества, краеведы, музеи ведут архив неродственника | Публичность и цитируемость важнее приватности |

**В первом релизе обслуживается только первый сегмент.** Остальные зафиксированы, чтобы позже не проектировать вслепую: выбор сегмента определяет приоритеты бэклога (онбординг, шаблоны словарей, массовое создание, биллинг), но на v1 не влияет.

> **[Требует решения при переходе к продажам]** Какие сегменты обслуживаются. От этого зависит и продукт, и канал продаж, и модель оплаты.

## 5. Scope

### 5.1 In Scope (первый релиз, сентябрь 2026)

**Мультитенантность:**
- `tenant_id` во всех таблицах с первой миграции
- Автоматическая фильтрация по тенанту на уровне ORM — разработчик не может случайно отдать данные чужого тенанта
- Резолвинг тенанта по `Host`-заголовку: поддомен и кастомный домен обрабатываются одним механизмом
- Создание тенанта — ручное (скрипт/SQL), UI не требуется

**Контент — четыре раздела:**
- Стихи (текст, название, дата написания, если известна)
- Фотографии, сделанные автором (галерея, просмотр в полном размере)
- Фотографии автора (галерея)
- Записи из блога (текст, дата, перенос из существующего блога)

**Функциональность:**
- Просмотр разделов на сайте (адаптивно: телефон, планшет, десктоп)
- Пагинация или ленивая подгрузка
- **Фасетная фильтрация и группировка контента** — навигация по архиву без поиска (механизм — ADR-0003)
- Административная панель: CRUD контента, управление видимостью, управление словарём тегов
- Импорт контента в систему
- Авторизация: **VK ID и Telegram** через общую абстракцию `AuthProvider`
- Ролевая модель и уровни видимости (см. раздел 6)
- Памятная книга: воспоминания от подтверждённых родственников
- Ручное подтверждение роли «родственник» владельцем
- Резервное копирование БД и медиа

**Техническая часть:**
- REST API как единый источник данных для всех клиентов
- OpenAPI-спецификация как контракт (API-first), версионирование в URL
- Хранение медиа в S3-совместимом хранилище через абстракцию `MediaStorage`
- Миграции БД с первого коммита
- **Dev-стенд**: отдельные БД, бакет, поддомен `dev.ochag.family` с тестовым тенантом, отдельные ключи VK/Telegram (провайдеры привязывают домен к приложению — общие ключи с продом невозможны). Настоящий контент на дев-стенде не размещается
- Серверная обработка изображений и фоновые воркеры в v1 не требуются: при объёме до ~1000 фотографий производные версии готовятся вне приложения

### 5.2 Out of Scope (первый релиз)

| Не входит | Причина / когда пересмотреть |
|---|---|
| **Полнотекстовый поиск** | Перенесён в v1.1. Компенсируется фасетной фильтрацией. Первый кандидат на следующий релиз |
| **Мобильное приложение** | Второй релиз, после того как API отлежится на реальном использовании |
| **Поддержка iOS** | Третий релиз. Решение о технологии (нативный Swift / KMP / Flutter) — тогда, а не сейчас |
| **Биллинг, тарифы, подписки** | Появляются вместе с третьим платящим клиентом, не раньше |
| **Self-serve регистрация и онбординг тенантов** | Тенанты создаются вручную скриптом |
| **Автоматическая выдача SSL для кастомных доменов** | v1 — wildcard-сертификат на поддомены, `a-vostok.ru` настраивается вручную |
| **Обслуживание сегментов 2–4** (см. 4.2) | v1 — только семья с техническим человеком |
| Механизм согласования публичности родственниками | v1 — решение владельца; модель данных заложена под расширение |
| Комментарии к отдельным записям | Обсуждение идёт в памятной книге |
| Автоматическая модерация | Круг участников подтверждён вручную |
| Аудио- и видеозаписи | Модель данных заложена под расширение |
| Многоязычность | Аудитория русскоязычная |
| Уведомления (email/push) | Нет сценария, требующего этого в v1 |
| Кастомизация оформления мемориала клиентом | Один шаблон оформления в v1 |
| Шаблоны словарей тегов для новых тенантов | Нужны при переходе к продажам, не в v1 |

> Все пункты означают «не в первом релизе», а не «никогда».

### 5.3 Явно вне рамок продукта (не бэклог)

- Физическая изоляция данных тенантов (отдельная БД/схема на клиента) — логической изоляции достаточно для этой предметной области
- Постоянно работающие ресурсы на каждый тенант — стоимость хранения одного мемориала должна оставаться близкой к стоимости объектного хранилища

## 6. Модель доступа и видимости

### 6.1 Роли

Роли действуют **в границах одного мемориала**: родственник в мемориале A не имеет прав в мемориале B.

| Роль | Права |
|---|---|
| **Владелец** | Наполняет контент, выдаёт роли, управляет видимостью и словарём тегов |
| **Родственник** | Читает всё, включая непубличное; оставляет записи в памятной книге |
| **Гость** | Читает только публичный контент |

Роль «родственник» выдаётся владельцем вручную по запросу.

### 6.2 Уровни видимости

У каждой единицы контента есть уровень видимости:

| Уровень | Кто видит |
|---|---|
| `PUBLIC` | все, включая неавторизованных |
| `FAMILY` | роль «родственник» и выше |
| `DRAFT` | только владелец (не опубликовано) |

Настройка задаётся на уровне единицы контента и на уровне раздела. **Дефолт при загрузке — `DRAFT`**: публикация всегда осознанное действие, случайная публикация невозможна.

Технически ограничение доступа к непубличным медиафайлам обеспечивается временными ссылками, выдаваемыми приложением после проверки роли: бакет остаётся приватным, прямой доступ по URL невозможен.

### 6.3 Принятие решения о публичности

В v1 решение принимает владелец единолично, консультируясь с родными вне системы. Механизм согласования между родственниками — в бэклоге.

Модель данных проектируется так, чтобы согласование можно было добавить, не меняя структуру видимости: **решение фиксируется как отдельная сущность** (кто, когда, что изменил), а не как перезапись поля. Механизм согласования надстраивается поверх истории решений; поверх одного поля `visibility` — нет.

## 7. Ключевые пользовательские истории (MoSCoW)

### Must have

- Как **гость**, я хочу открыть мемориал и увидеть разделы, чтобы познакомиться с наследием
- Как **гость**, я хочу читать стихи и записи блога в удобном для чтения виде
- Как **гость**, я хочу просматривать фотогалереи с открытием фото в полном размере
- Как **посетитель**, я хочу фильтровать контент по нескольким измерениям, чтобы навигировать по архиву
- Как **владелец**, я хочу добавлять, редактировать и удалять контент через панель управления
- Как **владелец**, я хочу управлять видимостью каждой единицы контента
- Как **владелец**, я хочу управлять словарём тегов своего мемориала
- Как **владелец**, я хочу быть уверенной, что контент не потеряется
- Как **владелец другого мемориала**, я хочу быть уверенным, что мои закрытые материалы недоступны посторонним тенантам

### Should have

- Как **посетитель**, я хочу авторизоваться через VK или Telegram, не создавая отдельный пароль
- Как **родственник**, я хочу оставить воспоминание в памятной книге
- Как **родственник**, я хочу видеть контент, закрытый для посторонних
- Как **владелец**, я хочу вручную подтверждать выдачу роли родственника
- Как **гость**, я хочу запросить доступ, если я близкий человек

### Could have

- Как **посетитель**, я хочу видеть даты и контекст фотографий
- Как **посетитель**, я хочу переходить между связанным контентом
- Как **владелец**, я хочу видеть, кто и когда получил доступ

### v1.1 (первые кандидаты после релиза)

- Полнотекстовый поиск по стихам и записям блога
- Автоматическое подключение кастомного домена к мемориалу

## 8. Нефункциональные требования

| Категория | Требование |
|---|---|
| Нагрузка | До 50 одновременных посетителей на мемориал; пики в памятные даты |
| Скорость | Первая отрисовка страницы раздела < 2с на мобильном 4G |
| Объём | До ~1000 фотографий и сотен текстов на тенант в v1. Архитектура не должна деградировать до ~10 000 единиц |
| Доступность | Плановая доступность 99% (простой до нескольких часов допустим) |
| **Изоляция тенантов** | Данные одного тенанта недоступны другому ни при каком запросе. Проверяется автотестами, а не ревью |
| Сохранность данных | Ежедневный автоматический бэкап БД и медиа; копии не менее 30 дней; **оригиналы медиа не удаляются никогда** |
| Стоимость хранения | Стоимость простаивающего мемориала — только объектное хранилище, без постоянного рантайма на тенант |
| Приватность | Персональные данные посетителей — минимум, необходимый для авторизации |
| Расширяемость | Новый тип контента, новый провайдер авторизации и новый тенант не требуют переработки API и клиентов |
| Поддерживаемость | Проект подхватываемый новым участником: документация, README с быстрым стартом, единый code style |

### 8.1 Стратегия хранения медиа

Единственный NFR, нарушение которого необратимо: сайт может полежать сутки, потеря оригиналов — потеря навсегда.

**v1:** одно S3-совместимое хранилище + автоматический бэкап в независимое место (другой провайдер).
**Заложено в архитектуру:** абстракция `MediaStorage` — добавление резервного провайдера не требует переписывания кода загрузки.

**Модель угроз.** Наиболее вероятная причина потери архива — не отказ провайдера, а массовая операция, выполненная ошибочно, либо потеря доступа к аккаунту. Отсюда требование к «независимости» копии: она не должна быть доступна ни платформе, ни через тот же аккаунт.

**Правило 3-2-1:**

| Копия | Где | Роль |
|---|---|---|
| 1 | Локальный диск | Рабочая |
| 2 | Внешний носитель, физически отдельно, **отключён** | Неприкосновенная |
| 3 | Объектное хранилище платформы | Раздача сайтом |

**Технические меры (обязательны):**
- **Версионирование бакета включено** — перезапись или удаление объекта не уничтожает предыдущую версию
- **Права на запись и на удаление разделены**: учётные данные, используемые для наполнения, не имеют права удаления на бакет с оригиналами
- Отработанный скрипт выборочного восстановления данных одного тенанта из бэкапа общей БД (следствие ADR-0001) — написать до появления второго тенанта

## 9. Домены

| Уровень | Схема | Когда |
|---|---|---|
| Платформа | `ochag.family` | Нужен к старту |
| Мемориал по умолчанию | `<имя>.ochag.family` | v1, wildcard-сертификат `*.ochag.family` |
| Кастомный домен первого мемориала | `a-vostok.ru` → CNAME на платформу | v1, настройка вручную |

**Резолвинг тенанта по `Host` — в v1** (ADR-0002). Первый мемориал открывается по кастомному домену, поэтому механизм «хост → тенант» нужен с первого дня. К v1.1 отнесены только автоматическая выдача сертификатов кастомным доменам и UI их подключения.

Зона `.family` снимает конфликт с занятым `ochag.ru` (магазин печей) и смысловую коллизию: `ochag.family` читается как семейный сервис.

Зоны `.xyz`, `.top`, `.online` не используем — проблемы с Telegram-виджетом авторизации и худшее восприятие.

## 11. Технические решения (детали — в ADR)

- **Backend:** Spring Boot + PostgreSQL
- **Мультитенантность:** общая БД, дискриминатор `tenant_id` (ADR-0001)
- **Резолвинг тенанта:** по `Host`-заголовку (ADR-0002)
- **Разметка:** фасетный контролируемый словарь, тенант-скоупный (ADR-0003)
- **Контракт API:** OpenAPI, API-first, версионирование в URL (`/api/v1/...`)
- **Веб-клиент:** Next.js (React)
- **Авторизация:** VK ID + Telegram Login Widget через абстракцию `AuthProvider`
- **Медиа:** S3-совместимое хранилище через абстракцию `MediaStorage`
- **Миграции БД:** Flyway или Liquibase с первого коммита
- **Поиск (v1.1):** полнотекстовый поиск PostgreSQL, без отдельного Elasticsearch
- **Мобильный клиент (v2):** решение о технологии отложено
