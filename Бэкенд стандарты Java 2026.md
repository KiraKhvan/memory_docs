# Бэкенд стандарты Java 2026

Принятые в индустрии практики для Java 21–25 (LTS) и Spring Boot — без привязки к коду проекта.

## Язык и дизайн

- **Неизменяемость по умолчанию.** Поля `final`, данные — `record`, коллекции — `List.of` / `Map.of`; наружу отдаются неизменяемыми или копиями.
- **Records для данных, sealed-иерархии для вариантов** + `switch` с pattern matching вместо `instanceof`-цепочек. Компилятор проверяет, что все варианты учтены.
- **Явный null.** `Optional` — только как возвращаемое значение (не поля, не параметры). Аннотации JSpecify (`@NullMarked`, `@Nullable`) + проверка NullAway — стандарт, к которому пришли Spring 7 и Guava.
- **Маленькие классы и методы**, одна причина для изменения; композиция вместо наследования. Наследование — только для настоящего «является», иначе класс `final`.
- **`var`** — где тип очевиден из правой части.
- **Исключения:** unchecked — для ошибок программы и предметной области; checked — только там, где вызывающий реально может восстановиться. Не глотать, не «логировать и пробрасывать», оборачивать с причиной (`cause`).
- **Виртуальные потоки (Java 21+)** для блокирующего ввода-вывода вместо пулов и реактивщины; structured concurrency и `ScopedValue` вместо `ThreadLocal` — там, где уже стабильны.

## Архитектура

- **Package-by-feature** (Spring Modulith, hexagonal, vertical slices) — сейчас преобладающая рекомендация: внутри фичи минимум публичного API, реализации package-private. Слоистые пакеты считаются устаревающими, но остаются распространёнными.
- **Интерфейс — когда есть больше одной реализации или граница модуля.** Пара «интерфейс + Impl» на каждый сервис сейчас скорее антипаттерн: Spring и Mockito давно не требуют интерфейсов.
- **Зависимости направлены к домену:** предметная логика не знает о вебе, БД и фреймворке.
- **Внедрение через конструктор**, не через поля.

## Spring Boot

- **Настройки** — `@ConfigurationProperties` на records с валидацией, не `@Value`.
- **Транзакции** — на уровне сервисов, короткие, без внешних вызовов внутри; реакции на коммит — outbox или `@TransactionalEventListener`.
- **Ошибки API** — RFC 9457 Problem Details.
- **Наблюдаемость:** Micrometer + OpenTelemetry, структурированные логи (встроены с Boot 3.4), health-пробы через Actuator.
- **Сборка:** GraalVM native и CDS/AOT — по необходимости, не по умолчанию.

## Тестирование

- **Интеграционные тесты на настоящей инфраструктуре** — Testcontainers, не H2 вместо Postgres.
- **Пропорции** — «тестовый трофей» / «соты»: больше интеграционных, меньше юнит-тестов с моками; моки — только на границах системы.
- **Инструменты:** JUnit 5 + AssertJ; ArchUnit — архитектурные правила проверяются в CI, а не на ревью.
- **Тестировать поведение, а не реализацию.**

## Качество и инструменты

- **Форматирование автоматически:** Spotless + google-java-format или Palantir — без споров о стиле на ревью.
- **Статический анализ в сборке:** Error Prone, NullAway, SpotBugs / PMD или Sonar — одно-два, но обязательно в CI.
- **Зависимости:** BOM, Dependabot или Renovate, сканирование уязвимостей (OWASP dependency-check, Trivy).
- **Javadoc** — на публичном API и для «почему», не пересказ «что».

## Принципы

- SOLID — в разумной мере; KISS и YAGNI важнее DRY.
- Для доменной сложности — DDD: агрегаты, инварианты внутри сущности, value objects на records.
- «Effective Java» (Joshua Bloch, 3-е издание) — по-прежнему база.
