# Проектирование ПО: артефакты, стандарты, подходы

Справочник по понятиям из обсуждения. По каждому: что это, зачем, как выглядит на практике.

---

## Часть 1. Артефакты по этапам

### Vision & Scope Document

**Что это.** Документ на 1–3 страницы, фиксирующий: какую проблему решаем, каким видим результат, что входит в проект и что явно не входит, кто заинтересованные стороны.

**Зачем.** Единственный артефакт, который отвечает на вопрос «а зачем мы вообще это делаем» в форме, к которой можно вернуться через полгода. В команде — основа для согласия: пока его нет, каждый участник держит в голове свою версию проекта.

**На практике.** Файл `/docs/scope.md` в репозитории. Обсуждается всеми участниками один раз на старте, дальше правится через PR, как код.

---

### In / Out Scope таблица

**Что это.** Две колонки: что делаем — что осознанно не делаем.

**Зачем.** Правая колонка важнее левой. Она фиксирует явные отказы. Без неё через месяц возникает разговор «а я думал, поиск тоже входит».

**На практике.**

| In Scope (v1) | Out of Scope (v1) |
|---|---|
| 4 раздела контента, просмотр | Полнотекстовый поиск |
| Загрузка контента админом | Модерация комментариев |
| Авторизация через VK | Мобильное приложение на iOS |

Указывайте версию/релиз в заголовке — «out of scope» почти всегда означает «не сейчас», а не «никогда».

---

### User Story

**Что это.** Формулировка требования с точки зрения пользователя по шаблону:
`Как <роль>, я хочу <действие>, чтобы <цель>`.

**Зачем.** Держит фокус на пользе, а не на реализации. Сравните: «сделать таблицу comments с FK на users» против «Как родственник, я хочу оставить комментарий, чтобы поделиться воспоминанием» — вторая формулировка позволяет обсуждать, нужна ли фича вообще.

**На практике.** Живёт в issue-трекере, не в файле. К каждой истории — критерии приёмки (см. Gherkin ниже).

---

### Use Case

**Что это.** Более формальный и подробный, чем user story, разбор сценария: актор, предусловия, основной поток шагов, альтернативные потоки, постусловия.

**Зачем.** User story отвечает «что и зачем», use case — «как именно, шаг за шагом, включая что делать при ошибках». Полезен там, где сценарий ветвится.

**На практике.** Для вашего проекта use case имеет смысл написать для одного-двух самых сложных мест — например, «выдача роли родственника»: там есть запрос доступа, уведомление админа, одобрение или отказ, повторный запрос. Для «посмотреть список стихов» use case излишен.

---

### NFR (Non-Functional Requirements) — нефункциональные требования

**Что это.** Требования не к тому, *что* система делает, а к тому, *насколько хорошо*: скорость, надёжность, безопасность, доступность, поддерживаемость.

**Зачем.** NFR определяют архитектуру сильнее функциональности. «Один пользователь одновременно» и «десять тысяч одновременно» — это два совершенно разных проекта при одинаковом списке фич.

**Главное правило: измеримость.** Плохо: «сайт должен быстро открываться». Хорошо: «первая отрисовка страницы раздела < 1.5с на 4G, 95-й перцентиль». Первое нельзя проверить и нельзя спроектировать под это.

**На практике.** Раздел в scope-документе или отдельный `/docs/nfr.md`. Для вашего проекта достаточно 5–7 пунктов: ожидаемая нагрузка, требования к скорости, политика бэкапов медиа, что происходит при недоступности S3, требования к приватности контента.

---

### Domain Model — доменная модель

**Что это.** Схема сущностей предметной области и связей между ними — концептуально, до всякой базы данных. `ContentItem`, `Poem`, `Photo`, `User`, `Role`, `Comment` и то, как они друг с другом соотносятся.

**Зачем.** Это словарь и структура мышления о проекте. Ошибка в доменной модели дороже любой другой: она протекает в API, в базу, в UI, в код клиентов.

**Отличие от схемы БД.** Доменная модель — про смысл («комментарий принадлежит записи и написан пользователем»). Схема БД — про хранение (типы полей, индексы, внешние ключи, нормализация). Первое рождает второе, но не совпадает с ним.

**На практике.** Диаграмма (или просто список сущностей с полями) в `/docs/domain-model.md`. Проверка зрелости: сможете объяснить модель вслух за минуту человеку не из проекта.

---

### Глоссарий терминов

**Что это.** Список терминов проекта с определениями. Буквально: «Запись — единица контента любого типа (стих, фото, блог-пост). Памятная книга — раздел с комментариями родственников».

**Зачем.** Самый недооценённый артефакт. В команде разные люди называют одну сущность разными словами: один пишет `post`, другой `entry`, третий `article` — и это расходится в коде, в API, в обсуждениях. Стоит полчаса на создание, экономит десятки часов путаницы.

**На практике.** `/docs/glossary.md`. Термины из глоссария обязательны в именах классов, полей API и таблиц — тогда код читается как предметная область.

---

### Definition of Done

**Что это.** Чеклист, что значит «задача готова». Например: код написан → тесты написаны и проходят → прошёл код-ревью → документация обновлена → задеплоено на dev-окружение.

**Зачем.** Без общего определения «готово» один участник считает задачу завершённой после написания кода, другой — после деплоя. В соло-проекте это не проблема, в команде — источник постоянных расхождений в оценке прогресса.

**На практике.** Несколько строк в `CONTRIBUTING.md` или чеклист в шаблоне PR (`.github/PULL_REQUEST_TEMPLATE.md`), чтобы он появлялся автоматически.

---

### Тест-стратегия

**Что это.** Документ на страницу: какие уровни тестирования применяем, что покрываем обязательно, что не покрываем осознанно, какие инструменты используем.

**Зачем.** Предотвращает две крайности: «тестов нет вообще» и «гоняемся за 100% покрытием ради цифры».

**На практике для вашего стека.**
- Unit-тесты — бизнес-логика в сервисах (JUnit + Mockito)
- Интеграционные — репозитории и API-эндпоинты (Spring Boot Test + Testcontainers с реальным PostgreSQL)
- E2E — один-два критичных сценария, не больше
- Осознанно не покрываем: геттеры/сеттеры, DTO, сгенерированный из OpenAPI код

## Часть 2. Стандарты и методологии

### ISO/IEC/IEEE 29148 и SRS

**Что это.** Международный стандарт на требования к ПО. Определяет структуру документа **SRS** (Software Requirements Specification) — полной спецификации требований: назначение, границы, функциональные требования, NFR, интерфейсы, ограничения.

**Зачем существует.** Регулируемые отрасли (медицина, авиация, оборонка, госзаказ), где полнота и трассируемость требований — юридическое обязательство, а не удобство.

**Стоит ли применять вам.** Целиком — нет. Полноценный SRS для некоммерческого проекта на несколько человек — это недели работы и документ, который никто не прочитает. **Но структуру стоит просмотреть один раз как чеклист** — она напоминает о категориях требований, о которых легко забыть.

---

### INVEST

**Что это.** Мнемоника для проверки качества user story:

- **I**ndependent — независима от других историй (можно делать в любом порядке)
- **N**egotiable — обсуждаема, не жёсткая техспека
- **V**aluable — несёт ценность пользователю
- **E**stimable — можно оценить трудоёмкость
- **S**mall — маленькая, влезает в один цикл работы
- **T**estable — проверяема, есть критерий готовности

**Зачем.** Быстрый фильтр. История «сделать бэкенд» проваливает почти все критерии сразу — значит, её надо декомпозировать.

**На практике.** Не документ, а привычка. Прогоняете новую историю по шести буквам за 20 секунд.

---

### Gherkin / BDD

**Что это.** **BDD** (Behaviour-Driven Development) — подход, где поведение системы описывается на языке, понятном и заказчику, и разработчику. **Gherkin** — синтаксис для этого:

```gherkin
Сценарий: Гость не может оставить комментарий
  Дано пользователь авторизован через VK с ролью GUEST
  Когда он открывает раздел "Памятная книга"
  Тогда поле ввода комментария неактивно
  И отображается кнопка "Запросить доступ"
```

**Зачем.** Двойная польза: это одновременно критерии приёмки (читаемые нетехническим участником) и исполняемый тест — фреймворки вроде Cucumber связывают текст сценария с кодом.

**На практике.** Не обязательно тащить Cucumber. Даже просто писать критерии приёмки в формате Given/When/Then в описании issue — уже даёт основную пользу: однозначность.

---

### ISO/IEC 25010 — модель качества ПО

**Что это.** Стандарт, раскладывающий «качество ПО» на восемь характеристик: функциональная пригодность, производительность, совместимость, юзабилити, надёжность, безопасность, поддерживаемость, переносимость. Каждая делится на подхарактеристики.

**Зачем.** Чеклист для NFR. Люди естественным образом помнят про производительность и безопасность, и естественным образом забывают про поддерживаемость и переносимость.

**На практике.** Проходите по восьми пунктам один раз при написании NFR, для каждого спрашиваете «есть ли здесь требование, которое повлияет на архитектуру». Часто ответ «нет» — и это нормально, важно, что вопрос задан.

---

### C4 Model

**Что это.** Подход к архитектурным диаграммам (автор — Simon Brown), четыре уровня масштаба:

1. **Context** — система как один блок и её окружение: пользователи, внешние сервисы. Для вас: «Мемориальный сайт» ↔ пользователи (админ, родственник, гость), VK ID, S3-хранилище.
2. **Container** — из чего система состоит на уровне развёртываемых единиц: Next.js-фронтенд, Spring Boot API, PostgreSQL, S3, Android-приложение. Кто с кем говорит и по какому протоколу.
3. **Component** — внутренности одного контейнера: модули внутри Spring Boot (auth, content, comments).
4. **Code** — классы. На практике почти никогда не рисуют: устаревает мгновенно, IDE показывает это лучше.

**Зачем.** Стал де-факто стандартом, потому что решает главную проблему архитектурных диаграмм — отсутствие единого масштаба. В одной диаграмме смешивают классы и сервера, получается нечитаемо. C4 требует определиться с уровнем.

**На практике.** Рисуйте уровни 1 и 2, третий — по необходимости. Инструменты: Structurizr (диаграммы как код), PlantUML с C4-библиотекой, Mermaid, либо просто Excalidraw/draw.io. Диаграммы-как-код предпочтительнее для команды — версионируются в git вместе с кодом.

---

### ADR (Architecture Decision Records)

**Что это.** Короткие markdown-файлы, по одному на значимое решение. Классический формат (Michael Nygard):

```markdown
# ADR-003: Kotlin + Compose вместо Flutter для мобильного приложения

## Статус
Принято, 2026-07-15

## Контекст
Нужно мобильное приложение под Android. Команда имеет Java-бэкграунд.
Рассматривались: Flutter, Kotlin Multiplatform, нативный Kotlin.

## Решение
Нативный Kotlin + Jetpack Compose. Только Android в v1.

## Последствия
+ Минимальный порог входа для Java-разработчиков
+ Полный доступ к платформенным API
− Появление iOS потребует отдельной разработки или миграции на KMP
```

**Зачем.** Самая высокая отдача на затраченное время из всех документов. Через полгода никто не помнит, почему выбрали X, а не Y — и без ADR обсуждение начинается заново. Плюс новый человек в команде читает `/docs/adr/` и понимает не только *что* построено, но и *почему именно так*.

**На практике.** `/docs/adr/0001-*.md`, нумерация по порядку. Один файл — одно решение, 10–20 строк. Не редактируются задним числом: если решение изменилось, пишется новый ADR со статусом «заменяет ADR-003».

**Что записывать.** Любое решение, которое дорого отменить: выбор языка, БД, архитектурного стиля, способа авторизации, схемы версионирования API.

---

### arc42

**Что это.** Шаблон архитектурной документации из 12 разделов: введение и цели, ограничения, контекст, стратегия решения, building blocks, runtime view, deployment view, сквозные концепции, архитектурные решения, качество, риски, глоссарий.

**Зачем.** Не столько для заполнения целиком, сколько как чеклист «о чём вообще стоит написать». Хорошо сочетается с C4 (даёт диаграммы для разделов 3, 5–7) и ADR (раздел 9).

**На практике.** Заполните разделы 1, 3, 4, 9, 12 — остальные по необходимости. Пустой раздел лучше отсутствующего: он напоминает, что тема не проработана.

### ADD и ATAM

**Что это.**
- **ADD** (Attribute-Driven Design) — метод проектирования, где архитектура выводится из приоритизированных требований к качеству (NFR), а не из функциональности. Итеративно: берём главный NFR → выбираем архитектурное решение под него → проверяем, не сломали ли остальные.
- **ATAM** (Architecture Tradeoff Analysis Method) — метод оценки готовой архитектуры на соответствие NFR через сценарии и анализ компромиссов.

**Зачем.** Формализуют правильную идею: **архитектуру определяют нефункциональные требования**. Классическая ошибка — выбрать микросервисы до того, как узнали, что пользователей будет пятьдесят.

**Стоит ли применять вам.** Как формальные процессы с воркшопами — нет, это для крупных систем. **Как принцип — обязательно**: прежде чем выбирать архитектурный стиль, выпишите NFR и спросите, какой из них диктует решение.

---

### DDD (Domain-Driven Design)

**Что это.** Подход Эрика Эванса к проектированию сложных доменов. Ключевые понятия:

- **Ubiquitous Language** — единый язык предметной области, одинаковый в обсуждениях, документации и коде. По сути — глоссарий, доведённый до дисциплины.
- **Bounded Context** — граница, внутри которой термин имеет одно конкретное значение. В одном контексте «Пользователь» — это профиль с фото и биографией, в контексте авторизации — набор credentials и роль. Разделение контекстов не даёт сущностям разрастаться в «god objects».
- **Aggregate** — кластер сущностей, изменяемых как единое целое, с одним корнем (Aggregate Root), через который идут все изменения. Например: `BlogEntry` (корень) + его `Comment`-ы — комментарий не существует сам по себе, доступ к нему только через запись.
- **Repository** — абстракция доступа к агрегатам (в Spring Data вы это уже используете, часто не думая о DDD).

**Зачем.** Для доменов со сложными правилами и инвариантами. Даёт язык для разговора о структуре и границах.

**Стоит ли применять вам.** Целиком — нет, домен слишком простой; полный DDD на CRUD-приложении даёт больше церемоний, чем пользы. **Отдельные элементы — да, и с большой пользой:** Ubiquitous Language (= глоссарий) и мышление в терминах агрегатов (комментарии живут через запись, а не сами по себе).

---

### Event Storming

**Что это.** Командная техника моделирования домена на большой поверхности (стена со стикерами или Miro/FigJam). Цветовая кодировка:

- Оранжевые — **события домена** в прошедшем времени: «Комментарий опубликован», «Роль выдана», «Фото загружено»
- Синие — **команды**, вызывающие события: «Опубликовать комментарий»
- Жёлтые — **акторы**, инициирующие команды
- Розовые — **внешние системы**: VK ID, S3
- Красные — **проблемные места**, вопросы без ответа

Порядок: сначала все события вразнобой, потом выстраиваются в хронологию, потом достраиваются команды и акторы.

**Зачем.** Работает именно как **командная** практика: за 1–2 часа выявляет расхождения в понимании домена, которые текстовый документ прячет. Красные стикеры — самое ценное: они показывают, где команда не знает ответа.

**На практике для вас.** Хорошая первая совместная сессия, когда подключатся другие участники. Дешёво, наглядно, на выходе — доменная модель, с которой все согласны.

---

### SOLID и GRASP

**Что это.** Принципы объектно-ориентированного проектирования на уровне классов.

**SOLID:**
- **S**ingle Responsibility — у класса одна причина для изменения
- **O**pen/Closed — открыт для расширения, закрыт для модификации
- **L**iskov Substitution — наследник должен корректно подставляться вместо родителя
- **I**nterface Segregation — узкие интерфейсы вместо одного широкого
- **D**ependency Inversion — зависеть от абстракций, не от реализаций

**GRASP** — набор из девяти принципов распределения ответственности между объектами (Information Expert, Creator, Controller, Low Coupling, High Cohesion и др.).

**Важное уточнение.** Это **не архитектурные** принципы, а принципы уровня кода. Они не помогут выбрать между монолитом и микросервисами. Их часто путают с архитектурой и цитируют не по делу.

**Где пригодится вам конкретно.** Dependency Inversion — прямо в том, что обсуждали: интерфейс `AuthProvider` с реализациями `VkAuthProvider`, `TelegramAuthProvider`. Сервис логина зависит от интерфейса, добавление провайдера не трогает существующий код. Это же Open/Closed на практике.

## Часть 3. Контракты и версионирование

### OpenAPI 3.1

**Что это.** Стандарт машиночитаемого описания REST API: эндпоинты, параметры, схемы запросов и ответов, коды ошибок, схемы авторизации. Формат — YAML или JSON.

**Зачем.** Единый источник истины о контракте между сервером и всеми клиентами. Из спеки генерируются: серверные интерфейсы, клиентский код, документация, моки для тестирования.

**На практике (ваш случай).** Вы выбрали API-first: спека пишется первой, из неё генерируются интерфейсы контроллеров Spring Boot и клиенты для веба и Android. Инструменты: `openapi-generator`, Swagger Editor / Stoplight Studio для написания.

---

### JSON Schema

**Что это.** Стандарт описания структуры JSON-данных: типы полей, обязательность, ограничения (мин/макс, regex, enum), вложенность.

**Зачем.** Лежит в основе OpenAPI 3.1 — блок `components/schemas` это и есть JSON Schema. Помимо API применяется самостоятельно: валидация конфигов, сообщений в очередях, входных данных.

**На практике.** Явно писать редко приходится — пишете схемы внутри OpenAPI-спеки. Знать, что это отдельный стандарт, полезно: валидаторы JSON Schema можно применить к любым данным, не только к API.

---

### AsyncAPI

**Что это.** Аналог OpenAPI для асинхронных, событийных взаимодействий: очереди сообщений, publish/subscribe, WebSocket. Описывает каналы, сообщения, их схемы.

**Зачем.** Если система обменивается событиями, контракт нужен так же, как для REST — иначе продюсер и консьюмер расходятся молча.

**Стоит ли вам.** Сейчас нет — синхронного REST достаточно. Понадобится, если появятся фоновые задачи через очередь (например, асинхронная обработка загруженных фото: генерация превью, извлечение EXIF) или push-уведомления.

---

### Semantic Versioning (SemVer)

**Что это.** Схема версионирования `MAJOR.MINOR.PATCH`:

- **MAJOR** — несовместимые изменения (клиенты сломаются)
- **MINOR** — новая функциональность, обратно совместимая
- **PATCH** — исправления, совместимые

**Зачем.** Версия сама сообщает, безопасно ли обновляться. Особенно важно для контрактов API и общих библиотек.

**На практике для вас.** Прямо связано с решением про версионирование API (`/api/v1/...`): major-версия API живёт в URL, minor и patch — прозрачны для клиентов. Правило: **удаление или переименование поля в ответе — это major**, добавление опционального поля — minor. Реальная причина, по которой это важно именно в вашем проекте: у родственников на телефонах будут старые версии приложения, которые никто не обновит.
